分支：`tail-index-routing`　　从 `165794a` 切出

## 一、为什么用这个基线

`165794a` 相对上游 `e811c32` **只改了 2 个文件**：

```
internal/kvstore/gcloop.go    | 17 ++++++----   摘掉 numGC>=2 的两轮上限
internal/kvstore/recovery.go  | 23 ++++++++++   每轮删掉被取代的排序文件
```

`e811c32` 的 `internal/kvstore/` 里**没有 partition/absorb 任何文件**，只有 `sparseindex.go`——它就是"没有分区 GC 的版本"。

选 `165794a` 而不是 `e811c32` 的理由：**`e811c32` 两轮之后 GC 永久停止**（`if kvs.numGC >= 2`），valuelog 无界增长，"尾部"就不再是一个有界的量，而本方案的整个前提是"尾部有界"。那两处 patch 只改空间与轮数，成本指标已验证在 ±3% 噪声内。

## 二、方案

### 要解决的问题

稳态下每次 GET 都并发跑两路（GC 期间三路），**未命中的一路照样跑完**——`read.go` 里 `st.spawn` 起的 goroutine 写进 buffered channel，没有 context 取消。于是：

```
每次 GET 的成本 ≈ 路 A（库查 + valuelog 读） + 路 B（排序文件查找）
```

**其中一路是白跑的。**

### 做法：用一次"不漏报"的判定替代一路

```
inTail(key) ?
  ├── 否 → 只查排序文件那一路        （安全：只有"不在"这个判定是硬的）
  └── 是 → 保持现状，跑两路
```

### 为什么必须是"判定"而不是"精确索引"

语义上只有一条硬要求：**"不在尾部"不能漏报**。因为 valuelog 优先——若 key 其实在尾部却判"不在"，就会去排序文件读到**旧版本**，破坏线性一致性。

反过来"误报在尾部"只多跑一次 valuelog，无害。

**这正是 Bloom filter 的定义**：没有假阴性，只有假阳性。于是索引从"必须精确且常驻"降级成"允许粗糙、允许丢失、允许重建"——这是小值场景唯一付得起的形式，因为精确的 per-key 索引要花掉它所覆盖数据（含记录头）的 `β/v` 倍内存。

### 分段

尾部是 FIFO 的（GC 从最老一端吃，新数据从最新一端追加），而 Bloom 不能删元素。所以：

```
seg0.log  seg0.bloom     <- 最老，GC 下一个就吃它
...
segN.log  segN.bloom     <- 最新，正在写

inTail(key) = OR over 所有现存段
```

- **写**：追加段日志 → `segN.bloom.Add(key)`（~50 ns）
- **GC**：absorb 开始时把当前段封口并开新段；absorb 完成后，丢弃所有完全落在 absorb 边界之前的段
- **判定**：逐段 OR。段数控制在 **8~16**，查询 ≈ 0.8 us

**absorb 边界必须与段边界对齐**——否则会出现"一段里一半被搬走、一半还在"，而 Bloom 无法只删一半。

### 安全退化（这条决定设计可实现）

> **任何一段的 bloom 缺失、校验失败、或尚未建好 → 该段一律判"可能在"，且不删它的日志。**

于是 bloom **可以是纯易失的**：重启、leader 切换后先整段保守，后台扫段日志重建（25 GB 尾部约 50 秒）。重建期间功能完全正常，只是退化成两路并发（= 现状）。**崩溃不破坏正确性，只掉性能。**

## 四、实验设计（单变量）

**加一个 flag `-tailRoute`（默认关）**，同一份二进制跑两组——避免用 commit 差异做对照。

| 组 | 参数 | 说明 |
|---|---|---|
| A 基线 | `-tailRoute=false` | 现状：两路并发 |
| B 路由 | `-tailRoute=true` | 判"不在尾部"就单路 |

**必须控制的两个变量：**

1. **读之前先排空尾部**（`data/gc_drain`）。否则尾部残留比例随写入速度漂移，读的是"半成品布局"——这是 `gcdrain.go` 里记下的教训。
2. **同一数据规模**。1 GiB 与 10 GiB 的 GC 窗口形态完全不同。

**要采的量：**

| 指标 | 为什么 |
|---|---|
| **`route_single_path_ratio`** | 有多少读被路由成单路——**它直接决定收益上限** |
| GET p50 / p99 / 吞吐 | 端到端效果 |
| 值大小 256B / 1KB / 4KB | 索引内存随 `1/v` 变，三档能看出边界 |
| `tailFilter` 内存占用 | 与精确索引的对比 |
| 写路径新增延迟 | 应 < 100 ns，需实测确认在噪声内 |

## 五、两条必须先想清楚的事

### 1. 门槛形式决定索引内存（与主线的张力）

```
绝对阈值 T    ->  尾部 <= T      ->  bloom 内存 O(T/v)      —— 有界
比例触发 r·S  ->  尾部 = r·S     ->  bloom 内存 O(r·S/v)    —— 随数据量涨
```

**"摊销有界"要求比例触发，"索引内存有界"要求绝对阈值。两者直接冲突。** 这是本方案绕不开的一条，写论文时必须正面回答（例如：把 bloom 也按比例预算，或用分级结构）。

先算量级（10 bit/key ≈ 1.25 B/key）：

| 场景 | 尾部 key 数 | bloom |
|---|---|---|
| T=1 GiB、64B 值 | 1140 万 | **14 MB** |
| r=0.25、S=100 GB、1KB 值 | 2370 万 | **30 MB** |
| r=0.25、S=100 GB、64B 值 | 2.66 亿 | **333 MB** |

### 2. 本分支已经摘掉的两轮上限是前提

`gcloop.go` 里那段注释掉的 `if kvs.numGC >= 2` 必须保持注释状态——否则 2 轮之后尾部无界增长，方案的前提直接不成立。

## 六、和主线的接口

本方案的可行边界与摊销定律用的是**同一组变量**：

```
摊销      = α + f/r + 差额/用户写
索引内存  = (β/v) × r·S
```

两者都含 `r`、`v`、`S`。所以它不该被当成孤立的小改进，而应与"索引的有界"放在同一节：**`r` 同时决定摊销和索引内存，是一个三目标（摊销 / 空间峰值 / 索引内存）的权衡参数。**
